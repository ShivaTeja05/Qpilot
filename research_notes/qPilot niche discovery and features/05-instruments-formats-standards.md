# 05 — Instruments, vendor software, file formats, APIs and data standards (as of 17 Oct 2026)

Researcher note on method and limits: this note was built from vendor user guides (PDF text extracted locally), vendor product pages, standards bodies' repositories (RDML consortium, Allotrope GitLab, SiLA GitLab), open-source reader source code, package indexes (PyPI/crates.io/CRAN/Bioconductor), peer-reviewed papers (Europe PMC full text), GitHub issues and two lab-automation forum threads. Every claim is labelled **[documented]** (primary source read), **[reported]** (secondary source, a forum post, or a single code comment) or **[unverified]** (could not be confirmed). The shared web-search budget ran out about a third of the way through this task, so the later half relied on direct fetches of known URLs; the "Open questions" section lists what that prevented (mostly list prices, Allotrope's member roster, and vendor AI/assistant features).

Vocabulary used below (defined once): **Cq/Ct/Cp** = quantification cycle (vendor names differ). **Rn** = reporter fluorescence divided by the passive-reference dye (ROX) signal; **ΔRn** = Rn minus a fitted baseline. **Multicomponent data** = per-dye signals after the spectral de-mixing of the raw filter readings (includes the passive reference). **Raw filter data** = the readings per excitation/emission filter pair before de-mixing. **RDML** = Real-time PCR Data Markup Language (zip containing `rdml_data.xml`). **RDES** = Real-time PCR Data Essential Spreadsheet, a TSV companion to RDML. **ASM** = Allotrope Simple Model (JSON schemas). **SiLA 2** = a lab-device communication standard (gRPC-based). **LIMS/LIS** = lab information (management) system.

---

## 1. How this corner of the niche works

### 1.1 The data path from instrument to analysis

Every real-time PCR instrument produces the same physical thing — one fluorescence reading per well, per filter/dye, per cycle (and per temperature step for melts) — and then hides it behind a vendor container and a vendor analysis layer. The scientist's week touches this path at four points: (1) plate setup (sample names, targets, tasks, barcode) typed into the vendor software or imported from a file; (2) the run, after which the native file lands on the instrument PC, a USB stick, a network share or a vendor cloud; (3) an export step in the vendor GUI (menu choices decide whether raw, normalised or baseline-subtracted values come out); (4) analysis in the vendor software or in a third-party tool fed by that export. Integrators (Benchling, TetraScience, Ganymede) almost universally hook step 3 by watching an export folder, not by reading native files [42][44][45].

**What "raw" means per vendor (this matters for LinRegPCR-style analysis, which needs un-baselined curves):**

- Thermo/Applied Biosystems exports distinguish three layers: *Raw data* = "fluorescence readings … that have not been normalized to the passive reference", one column per `<excitation filter>-<emission filter>` bin; *Multicomponent data* = "the raw fluorescence of all reporter dyes … including reporter dyes, quencher dyes (except non-fluorescent dyes), and the passive reference"; *Amplification data* = Rn ("raw fluorescence readings … normalized to the fluorescence from the passive reference") plus ΔRn if available [1] **[documented]**. Design & Analysis 2 exposes the same layers as export tabs: Results, Amplification Data, Multicomponent, Raw Data, Replicate Group Result [2] **[documented]**.
- Bio-Rad CFX Maestro's per-cycle values are "RFU" and the baseline mode in force when you export ("No Baseline Subtraction", "Baseline Subtracted", "Baseline Subtracted Curve Fit") "determines the method of baseline subtraction for all fluorescence traces" [9] **[documented]**. In other words a CFX "amplification" export is only raw if the analyst switched baseline mode first; RDML exports "include analysis data with the baseline settings that you apply in the Data Analysis window" [9] **[documented]**.
- Roche LightCycler 480 stores readings in instrument units and its text export multiplies them by `ScalingFactor / (RefValue × IntgrTime)`; the stored values carry no colour compensation [48-ixo] **[documented, from a permissively licensed reader's source comments]**. The text export contains raw fluorescence, not Cp [59][58] **[documented]**.
- Qiagen Rotor-Gene `.rex` files "keep raw readings only: no Cq, threshold or Tm from the vendor analysis" [48-rex] **[documented, reader source]**.
- RDES (the MIQE 2.0 spreadsheet format) demands exactly this: values "must be raw, corrected only for machine background, with no baseline correction and no negative values" [31-RDES] **[documented]**.

### 1.2 Roles and where decisions are made

- **Bench scientist / student**: sets up plates, runs, exports, then analyses in vendor software or Excel; picks baseline/threshold defaults; rarely exports raw data (MIQE 2.0 and the 2023 HEROIC "call for action" both say raw data sharing remains the exception [37][36]).
- **Core-facility manager**: owns the instrument PC and the vendor software licence/edition; decides whether auto-export is configured (QuantStudio 6/7 Pro export settings, CFX Maestro "Automatically export LIMS data at end of run", qPCRsoft "autom. raw data csv export at the end of run") [2][9][22] **[documented]**.
- **Lab-automation engineer**: integrates instruments into schedulers; the 2024 Lab Automation Forums thread describes the QuantStudio 7 Pro as the most-used option with existing scheduler drivers, notes that EDS files are zip archives, and reports that LightCycler protocols "output two files that must be manually merged before LIMS upload", that qTower software "can generate positive curves out of negative raw data", and that Bio-Rad baseline problems "may lead to false results" so the lab relies on human review [51] **[reported, forum]**.
- **Informatics/LIMS admin**: configures LIMS plate files (Bio-Rad `.plrn`, Thermo plate-setup `.txt`), export folders and gateways [9][1][42].

### 1.3 Standards in play

- **RDML** (rdml.org; MIT-licensed schema repo). Versions: 1.0 (2009), 1.1, 1.2 (autumn 2014), 1.3 (REC) and **1.4, which is still a Candidate Release** (`RDML_v1_4_CR.xsd`) [31][35] **[documented]**. 1.3 added digital-PCR partitions (tab-separated tables in a `partitions/` folder inside the zip), `N0`, `ampEff`, `ampEffSE`, `corrF/corrP/corrCq`, `meltTemp`, `dyeChemistry`, per-target sample types and target-specific quantities [31-1.3] **[documented]**. 1.4 adds only optional elements: `Ncopy`, `nCopyFact` (defaults 0.10 probes, 1.5 SYBR, 0.04 EvaGreen), `dyeConc`, `oligoConc`, reaction `vol`, sample `doubleStranded` [31-1.4] **[documented]**. Container rules: `rdml_data.xml` inside a PKZIP archive named `.rdml` (preferred) or `.rdm`; software should also accept bare `.xml`; semicolon-separated multi-values [31-notes] **[documented]**.
- **RDES v1.0** (REC): one TSV per run for amplification and one for melting; seven fixed columns (Well, Sample, Sample Type, Target, Target Type, Dye, Cq|Tm) then raw fluorescence by cycle/temperature; sample types `unkn, ntc, nac, std, ntp, nrt, pos, opt`; target types `toi|ref`; Cq `-1.0` = failed [31-RDES] **[documented]**.
- **MIQE 2.0** (Bustin et al., Clin Chem 2025;71:634–651): authors should make raw fluorescence data available, names RDES and RDML as the vendor-independent formats and "asks instrument manufacturers to support export in one of them"; discourages 2^-ΔΔCq; Cq should be converted to efficiency-corrected quantities with prediction intervals; encourages sharing analysis scripts [37] **[documented]**.
- **Allotrope ASM qPCR/dPCR**: JSON schemas published quarterly under `json-schemas/adm/pcr/REC/` from 2021/12 to 2026/09 (qPCR) and 2023/12 to 2026/09 (dPCR) [40-tree] **[documented]**. Licence is the main practical issue (see §4 and Discovery 3).
- **SiLA 2**: base feature definitions (MIT) contain no PCR/qPCR features; the public device catalogue lists one thermocycler (Inheco ODTC, no optics) and one generic "Microplate Reader", no qPCR instrument [46] **[documented]**.
- **ISO 20395:2019** ("Biotechnology — Requirements for evaluating the performance of quantification methods for nucleic acid target sequences — qPCR and dPCR"): generic requirements covering analytical design (calibration curves vs molecular counting), controls, sample quality, assay design, data handling (quality control, acceptance criteria, threshold setting, normalisation), validation (precision, linearity, LOQ, LOD, trueness, robustness) and metrological traceability/uncertainty; excludes oligonucleotides <50 bases; paid document, full text not reviewed [47] **[documented scope only]**.

### 1.4 Instrument-by-instrument map

Legend: Native = the file the vendor software saves. Export = what the GUI/CLI writes. RDML = export support and version. Prog. = programmatic routes. Readers = open-source code that reads the native file (licence). Raw reach = which raw layers are reachable without the vendor GUI.

**Thermo Fisher / Applied Biosystems — QuantStudio 1/3/5/6 Flex/7 Flex/12K Flex, 6 Pro/7 Pro, ViiA 7, StepOne(Plus), 7500, 7900HT, OpenArray**
- Native: `.eds` (templates `.edt`, "pretty much just EDS files with a different extension" [50] **[reported]**). `.eds` is a zip. Three layouts are documented by a permissively licensed reader: the SDS/XML layout (`apldbio/sds/experiment.xml`, `plate_setup.xml`, `analysis_protocol.xml`, `tcprotocol.xml`, `multicomponentdata.xml`, `analysis_result.txt`, `meltcuve_result.txt`, plus a `Manifest.mf`), the 7500/StepOne text layout (`apldbio/sds/multicomponent_data.txt`, records `WELL CYCLE DYE MSE SIGNAL`), and the JSON layout written by Design & Analysis 2 and the 6/7 Pro (`summary.json`, `run/run_summary.json`, `setup/plate_setup.json`, `setup/run_method.json`, `primary/analysis_setting.json`, `primary/multicomponent_data.json`, `primary/analysis_result.json`, `extensions/am.rq/…`, `extensions/am.sc/…`); `apldbio/sds/images/` holds raw optical images that nobody decodes [48-eds] **[documented, reader source]**. The qslib author gave the same split (EDS 1.x = text+XML for ViiA7/QS3/5/6/7 Flex; EDS 2.x = text+JSON for QS6/7 Pro) [50] **[reported, forum]**. Jay_qPCR adds that D&A 2.4 files use `analysis_result.json`, `plate_setup.json`, `summary.json` [52] **[reported]**. Quirks: JSON layout writes bare `NaN`/`Infinity`; "Undetermined" is stored as Ct = cycle count (40.0 of 40); SDS/7500 layouts do not store the automatic threshold [48-eds] **[documented, reader source]**.
- Export (D&A 2, v2.8, Jan 2024): Actions ▸ Export with an *export settings* file controlling tabs (Results, Amplification Data, Multicomponent, Raw Data, Replicate Group Result), one file per item or combined, options for rounding, quoting, two-digit well positions, section headers, empty/omitted wells; file formats include `.xlsx`, `.xls`, `.txt`, `.csv` [2][42-DA] **[documented]**. "Export settings can be applied to data exported by the software or by an instrument" and can be downloaded and imported into a QuantStudio 6/7 Pro so the instrument auto-exports at run end (Benchling documents the instrument's "Export run results with… Auto Export Settings" screen, XLS, to a target directory) [2][42-DA] **[documented]**. Compatible data files: QS 7 Flex, 6 Flex, 12K Flex (TaqMan Array Card and OpenArray), QS5, QS3, QS1, StepOnePlus, ViiA 7, 7500/7500 Fast, 7900HT — legacy files open but "can only be saved as the updated file format"; OpenArray pre-run files cannot be created in D&A 2 [2] **[documented]**.
- RDML: D&A 2 exports RDML only "for standard curve, relative standard curve, and comparative Ct analysis" [2] **[documented]**; the 2015 command-line guide likewise restricts RDML to "Standard Curve, Gene Expression, and Relative Standard Curve experiments" [1] **[documented]**. Version written: rdml.org lists StepOne, QuantStudio 12K Flex and ViiA 7 with no version [30]; a vendor blog claims pre-2.6 D&A "sometimes export RDML v1.1 files that are missing melt curve data" and that current software "typically exports v1.3 or v1.4" [62] **[reported, secondary; version unverified]**.
- CLI: `cmdlineutil.exe` ships with "QuantStudio Design and Analysis desktop Software v1.2.x" for QS3/5 (MAN0010409, Dec 2015). `-expgen` creates `.eds` batches from `.edt` template + plate-setup `.txt` + sample `.txt` + barcode `.txt` + assay-information `.aif/.aix`; `-export -e <dir> -f QuantStudio|RDML -l <out> -s single|multiple -x txt|xls|xlsx|rdml` exports every `.eds` in a folder; the guide's stated purpose is LIS integration and it mentions "the API, when running in headless mode" [1] **[documented]**. Whether the CLI still exists in D&A 2.x: **[unverified]** (the D&A 2 guide has no command-line section).
- Instrument API: the QuantStudio 1 guide documents an "OEM Connection Only" setting: "Required for API access to the instrument. When enabled, the software (desktop and Thermo Fisher Connect) cannot connect to the instrument. API access to the instrument is exclusive to authorized OEM partners." [5] **[documented]**. qslib talks SCPI to the instruments over port 7443 (firmware ≥1.3.4, SSL) or 7000 [49] **[documented]**; its author reports SSLv3-only connections and that device passwords "are in no way secure" [50] **[reported]**.
- Cloud: Thermo Fisher Connect — Individual edition free with 25 GB; Enterprise edition is a paid annual subscription with unlimited storage, SSO and "integration APIs" [6] **[documented]**. DA3, branded "Diomni Design and Analysis 3.x", runs on desktop (Win/Mac), on-premises or in the cloud "hosted on ThermoFisher Connect"; advertises CNV/genotyping, multi-plate analysis, an "improved Ct algorithm" and "advanced spectral conditioning (cross-talk reduction)"; it does not control QS5 instruments and supports SAE for QS7 Pro only on-premises [3][4] **[documented]**. A "Diomni v4.3" Presence/Absence export exists as a Benchling test fixture [41-DAtest] **[documented]**. QS 6/7 Pro: Connect-compatible, Instrument Connect app for remote monitoring, facial authentication and voice commands, 21 CFR Part 11 software included with QS7 Pro (upgrade option on QS6 Pro), Orbitor RS2 automation [7] **[documented]**.
- Readers: **OpenReadout** `openreadout-qpcr` (MIT OR Apache-2.0; v0.1.0 3 Oct 2026 → v0.3.0 13 Oct 2026; reads `.eds` for "QuantStudio 1-7 Pro, 12K Flex, ViiA 7, StepOne, StepOnePlus, 7500", results exports, RDML, `.ixo`, `.rex`, `.lc96p`; refuses `.pcrd`; writes RDML 1.3 and ASM; ships an MCP server with 28 tools; 1 GitHub star, 57 crate downloads) [48] **[documented]**. **qslib** (EUPL-1.2; PyPI 0.15.3 on 29 Jul 2026; EDS 1.x read/write, EDS 2.x read; Rust core since 0.14; "I am not any way connected with Applied Biosystems"; EUPL cannot be used by qPilot) [49] **[documented]**. **Jay_qPCR** (GPL-2; `EDSReader.py` reads `analysis_result.txt`, `plate_setup.xml`, `experiment.xml`) [52]. **Juul/eds-handler** (Node, no licence stated; 7500; describes `.eds` as an OOXML-shaped zip with an `apldbio/sds` directory) [53]. **Q-Prism SNP visualizer** (`parsers/quantstudio.py` for QS3 `.xls`; licence unverified) [54]. **RDML R package** (MIT; reads ABI 7500 `.xls` exports with 'Sample Setup' and 'Multicomponent Data' sheets) [39]. **allotropy** (MIT; parses QuantStudio RT-PCR Software 1.7.2 txt/xlsx and D&A 1.5.2/2.7.0 xlsx/xls into ASM) [41]. **HTqPCR** (Artistic-2.0; SDS and OpenArray Ct tables) [27].
- Raw reach: native `.eds` → multicomponent per dye incl. ROX, Rn/ΔRn, melt, results (no GUI needed); D&A 2 export → Raw filter data + Multicomponent + Rn/ΔRn + Melt Curve Raw Data (Reading, Fluorescence, Derivative) [41-QS] **[documented]**; instrument auto-export → same via export settings; CLI (D&A 1.2.x) → batch txt/xlsx/RDML.

**Bio-Rad — CFX96/384 Touch, CFX96 Touch Deep Well, CFX Connect, CFX Opus 96/384/Deepwell, CFX Duet (CFX Maestro 2.3; CFX Manager 3.x legacy)**
- Native: `.pcrd` ("Contains the results of an experiment run and PCR analysis"); also `.prcl` protocol, `.pltd` plate, `.mgxd` gene study, `.zpcr` "stand-alone pre-data file … fluorescence readings from stand-alone operation that are converted into a data file", `.plrn` LIMS file [9] **[documented]**. `.pcrd` is an encrypted container: OpenReadout detects and refuses it ("Encrypted … the key is not public"; exit 6) and its provenance log states "No key or password was searched for or used" [48-prov] **[documented]**; third-party file-extension sites say older files were XML and newer ones encrypted archives [63] **[reported, low reliability]**. An RDML-package maintainer also reported that files saved by Maestro cannot be reopened by CFX Manager [39-#27] **[reported]**.
- Export (Maestro 2.3): *Export All Data Sheets* writes "all the spreadsheet views from every tab" as CSV, TXT, XLSX (one workbook per sheet, or combined), XLS or XML; *Export RDML File* "select either version 1.1 or 1.0"; *Custom Export* (txt/csv/xls/xlsx/xml, choose fields, optionally rename columns); *Export to LIMS Folder* [9] **[documented]**. The Quantification tab has four spreadsheet views — Results, Standard Curve Results, Plate, and "RFU — displays the RFU quantities in each well for each cycle" (well per column, cycle per row); the Melt Curve tab has RFU-per-temperature and −d(RFU)/dT sheets [9] **[documented]**. Results columns: Well, Fluor, Target, Content (sample type + replicate), Sample, … [9]. Run end actions: email the `.pcrd` as an attachment; CFX Opus can copy data to a USB drive or a shared network folder [9][10] **[documented]**.
- LIMS integration (Appendix C): requires a LIMS plate file `.plrn` (CSV with a fixed layout: PlateType, ScanMode, Units, RunID, RunNotes, RunProtocol, DataFile, then per-well Ch1–Ch5/FRET dye, SampleType, SampleName, per-channel Target, CollectionName, Replicate, per-channel Quantity, Well Note, per-channel colours), a `.prcl` protocol, an export folder (default `C:\Users\Public\Documents\Bio-Rad\CFX\LIMS`) and an export format; option "Automatically export LIMS data at end of run"; "Only LIMS data exported as a .csv file can be imported back into CFX Maestro" [9] **[documented]**. Content of the LIMS data export (results only vs curves): **[unverified]**.
- RDML: v1.1/v1.0 selectable; rdml.org lists CFX Maestro at 1.1 [30]. Caveat: a 2020 issue showed Maestro 1.1 RDML files containing "only Cq values, with no fluorescence data points" while CFX Manager 3.0 files imported fine; Bio-Rad did not reply [39-#27] **[reported, one issue]**; rdmlpython issue #3 found Bio-Rad RDML archives whose inner XML was not named `rdml_data.xml` (fixed by `load_any_zip`, Mar 2023) [32-#3] **[documented]**; RDML-Tools 1.1.0 added a repair for the same deviation [33-RN] **[documented]**.
- Programmatic: no public API or CLI found. covmatic/PCR_station (MIT) drives a CFX96 "via the BioRad application by exchanging XML files (via USB serial connection)" and then reads the CSVs the run generates [55] **[documented]**. Benchling's connector reads a Maestro CSV with columns Well, Fluor, Content, Sample, Biological Set Name, Cq; melt, end point and replicate statistics are not supported [42-CFX] **[documented]**.
- Cloud: BR.io "cloud-based instrument connectivity, data management, and analysis platform", early access announced 7 Oct 2020 with CFX Opus; bulletin 7279 lists BR.io, email and USB as data routes and says Maestro can export to LIMS [12][10] **[documented]**; the BR.io site requires JavaScript and could not be read **[unverified features]**.
- Editions/prices: CFX Maestro 2.3 standard (cat. 12013758), Security Edition 1 user (12012832, HASP HL key, file encryption, audit trail, e-signatures) and 5 users (12013028); prices not displayed [11][10] **[documented catalogue numbers; prices unverified]**.
- Readers: OpenReadout reads the `Quantification Cq Results` export only (no curves) [48-fmt]; allotropy reads the Cq CSV [41-CFX]; HTqPCR reads CFX Ct tables [27]; RDML-TableShaper has a "BioRad CFX v3.1" preset for the per-cycle RFU table (flip layout, cycle in column 1) [33-TS]; RDML R package ships `BioRad_qPCR_melt.rdml` and `BioRad.xlsx` fixtures [39-extdata].
- Raw reach: only through Maestro GUI exports (RFU sheet, with baseline mode set to "No Baseline Subtraction" first) or RDML (version-dependent completeness); `.pcrd` itself is unreachable without the vendor software. This is the one major vendor where GUI automation is unavoidable for retrospective data (end-of-run auto-export only covers future runs).

**Roche — LightCycler 480/480 II, LightCycler 96, LightCycler PRO, Digital LightCycler**
- LC480 native: `.ixo` = "an XML object stream" of `<obj>/<prop>/<list>` elements ending in a checksum line; the acquisition store is "base64 of a zlib stream"; `THTCFloAcquisition` holds `Channel`, `Temp` (hex-encoded big-endian f64), `Valid`, `FloPoints` (base64 little-endian f32, one per plate position; invalid acquisitions → NaN); vendor Cp/calls live in `QuantSampleB` (`CrossingPoint`, `Call` 2 = amplified, 0 = not); no colour compensation is stored; export scale = `ScalingFactor / (RefValue × IntgrTime)` [48-ixo] **[documented, reader source]**. Exports: native `.ixo`, "full data in plain-text .txt", Ct table as .txt [60]; the text export contains raw fluorescence (columns the tidyqpcr reader expects: well, sample, program, segment, cycle, time, temperature, raw fluorescence "in arbitrary units") [58]; "Fluorescence history (over Cycles) as XML" is another export (QPCRWebApp; "point index" checkbox required) [57] **[documented/reported]**. A 2011 pyQPCR thread confirms the text export "contains the raw fluorescence data and not the Ct values" [59] **[reported]**. LC480 Software 1.5 add-on modules and prices: **[unverified]**.
- LC96 native: `.lc96p` = an RDML 1.1 zip with extra Roche XML members [48-fmt][39-#21] **[documented]**; rdml.org lists LC96 at RDML 1.1 [30]. Deviation: files re-saved in LightCycler 96 software 1.1.0.1320 without running an analysis lack expected fields (prefixes d2/d3), crashing RDML R until a 2017 fix; workaround: run any analysis before saving [39-#21] **[documented]**. Product page: modules Relative Quant, Absolute Quant, HRM, Qualitative Detection, Melting Peak, Endpoint Genotyping; email notification; "server-based network interfacing" [16] **[documented]**. An unanswered Feb 2026 issue reports an LC96 file that fails to open in RDML R [39-#36] **[reported]**.
- LightCycler PRO (software 1.2; guide publication 2.0, 2025): run data exported "to SFTP server or USB device" from the Results app, either "for further analysis on the development software or as customer data export"; a separate "LightCycler PRO Development Software" builds run profiles and "analysis packages"; "Synchronizing plate setups with host"; the product page lists an HL7-based host interface to a customer LIS, remote access for monitoring and review, adaptive colour compensation over 7 channels and an "updated derivative algorithm that automatically determines Cq values"; documentation is distributed through the navify Portal/eLabDoc [14][15] **[documented]**. Export file formats of the "customer data export": **[unverified]**. Whether the PRO replaces the 480: not stated [15].
- Readers: OpenReadout (`.ixo` medium confidence; `.lc96p` via RDML) [48]; tidyqpcr (`read_lightcycler_1colour_raw`; licence in LICENSE.md not read) [58]; RDML R (`.lc96p`) [39]; HTqPCR (LightCycler Ct tables) [27]; an MIT `ixo_parser.py` exists in Echo-nannan/rt-qpcr-protocol-guide [48-prov] **[reported]**. TableShaper presets: "Roche LightCycler480" (three layouts), "Roche LCS480 Amplification/Meltcurve v1.5.0.39", "Roche LC96" [33-TS].
- Raw reach: LC480 `.ixo` and text export both yield raw per-cycle readings without the GUI; LC96 yields RDML 1.1 with raw `adp` data; PRO: unknown format via SFTP.

## 3. Discoveries (ranked by impact × feasibility × fit)

### Discovery 1 — The "raw-reachability contract": per-vendor capture recipes plus an Import Trust Card that proves what was captured is raw

1. **Persona and situation.** A postdoc or core-facility analyst with plates from two or three instrument families (typically QuantStudio + CFX, sometimes a LightCycler 480) who wants qPilot's whole-study LinRegPCR analysis but has only vendor exports, some made months ago with unknown settings. Weekly.
2. **Evidence of the pain.** P1–P3, P7. Concretely: the CFX "RFU" sheet is whatever baseline mode was active [9]; QuantStudio files store "Undetermined" as Ct = cycle count and may lack the automatic threshold [48-eds]; Maestro 1.1 RDML carried Cq only [39-#27]; LC480 exports are scaled by `ScalingFactor/(RefValue×IntgrTime)` [48-ixo]; the LinRegPCR authors state raw, not-yet-baselined fluorescence "must be available in a readable format" [34]. Estimate (labelled): a lab that re-exports 20 plates by hand at 3–5 minutes each loses 1–2 hours per study, and a baselined-twice import silently biases every efficiency estimate.
3. **What exists today.** Vendor exports; RDML-Tools TableShaper with 21 layout presets (GPL-3 web tool, manual mapping) [33]; OpenReadout (MIT/Apache, 2 weeks old, reads `.eds/.ixo/.rex/.lc96p/RDML` and AB/CFX result exports, refuses `.pcrd`) [48]; allotropy (MIT, Cq-centric for CFX) [41]; VoilaPCR (web, closed) [62]. None verifies raw-ness, none records which export recipe produced the data, and none ties the capture to a decision.
4. **The concrete feature.** (a) *Capture recipes* shipped as data, one per (vendor, software version, route): the exact menu path/settings and the expected file signature — e.g. "D&A 2.x: Actions ▸ Export, export setting with Raw Data + Multicomponent + Amplification + Melt Curve Raw Data tabs, combined file" [2][42]; "CFX Maestro 2.x: set Baseline Settings = No Baseline Subtraction, then Export ▸ Export All Data Sheets ▸ CSV; keep the `Quantification Amplification Results` and `Melt Curve RFU` sheets" [9]; "LC480: export .ixo + text; apply export_scale" [48-ixo]; "RGQ: `.rex` directly" [48-rex]; "qTOWER: enable autom. raw data csv export, type RD" [22]; "Aria: LIMS export, Amplification Plots, vertical layout" [20]; "Chai: GET /experiments/:id/export" [28-ctrl]. (b) *Readers* for the permissively documented containers: `.eds` (all three layouts), `.ixo`, `.rex`, `.lc96p`, RDML, AB txt/xlsx, CFX CSV/XLSX — either by depending on `openreadout` (MIT OR Apache-2.0, Python wheel, `>=3.10`) [48-PyPI] or by re-implementing from the same public sources (its clean-room policy lists them) [48-prov]. (c) *Raw-ness detector* as a deterministic method module: tests per curve for signs of prior baseline subtraction (early-cycle mean ≈ 0 with symmetric negatives; plateau/baseline ratio), prior passive-reference normalisation (Rn scale ~1), scaling (LC480 export_scale present), and missing layers (Cq-only RDML: `react/data` without `adp`). Output = an **Import Trust Card** per plate: "This CFX export was baseline-subtracted by Maestro (evidence: 71/96 wells have negative values in cycles 1–5). Options: re-export with No Baseline Subtraction [recipe link]; proceed with vendor-baselined curves (LinRegPCR baseline step disabled; Study Confidence capped at 'moderate'); use vendor Cq only." The chosen option, the file hash, the recipe id and the detector facts go into the Analysis Record; `qpcr_study` exposes `capture_recipes()` and `import_trust(plate_id)` to agents. (d) A published *compatibility matrix* generated by CI from public fixtures (vendor Cq vs qPilot Cq agreement per instrument, like OpenReadout's results table [48-fmt]).
5. **Feasibility.** Fixtures with licences: 214 CC-BY `.eds` on Figshare surveyed by OpenReadout; `.eds` + AB exports at Zenodo 4598136 (CC0), Harvard Dataverse doi:10.7910/DVN/QE5CEQ (CC0), Figshare 21205784/21205928/21202280/30581381/14977929 (CC-BY), Zenodo 18006983/14230362 (CC-BY); `.lc96p` at Zenodo 14965510 (CC-BY); `.ixo` at Zenodo 22121623 (CC-BY, with an HTML reader) and Mendeley doi:10.17632/rtsx7zpt4w.1 (CC-BY); `.rex` Figshare 30598193 (CC-BY); `.pcrd` Figshare 31082878 (CC-BY, for refusal tests); CFX CSV in churchlab/Vascularized-Organoids (MIT); allotropy test data (MIT: QuantStudio txt/xlsx, 22 D&A xlsx across QS1…QS7 Pro and Diomni 4.3, CFX csv, Diomni xlsx); RDML R extdata (MIT: `sce.eds` 7500, `BioRad_qPCR_melt.rdml`, `lc96_bACTXY.rdml`, `stepone_std.rdml`, `BioRad.xlsx`) [48-prov][41][39-extdata]. Libraries: openreadout (MIT/Apache), rdmlpython (MIT), openpyxl (MIT), xlrd (BSD). Effort: recipes + detector + card ≈ 2–3 weeks; readers via openreadout ≈ days, own re-implementation ≈ 4–6 weeks. Hardest part: validating the raw-ness heuristics across vendors without false alarms; openreadout's youth (v0.3.0, 1 star) means pinning and vendoring tests.
6. **Why qPilot.** Raw curves are the engine's input; "decisions only where they change conclusions" is exactly where a capture ambiguity sits; the record already hashes inputs; MCP exposure lets an agent refuse to analyse untrusted imports.
7. **Risks / confidence.** Vendor EULAs (not retrieved; see Open questions) may forbid reverse engineering of software — the plan reads files produced by ordinary use and uses no vendor code, matching OpenReadout's stated clean-room policy [48-prov], but counsel should confirm; `.pcrd` must stay refused (DMCA anti-circumvention risk noted by OpenReadout) [48-prov]. Confidence **high** that the pain is real and the route is feasible; **medium** on heuristic accuracy.

### Discovery 2 — RDML dialect normaliser and conformance report (and shipping the RDML 1.4/Ncopy path that pip does not give you)

1. **Persona.** The same analyst, plus a journal reviewer or data steward receiving RDML supplements; a tool maintainer (qPilot itself) depending on rdmlpython.
2. **Evidence.** P2, P4, P8: vendor RDML implementations "differ significantly" [39]; Maestro Cq-only files [39-#27]; inner XML not named `rdml_data.xml` [32-#3][33-RN]; LC96 fields missing unless analysed before saving [39-#21]; Thermo exports RDML only for three experiment types [2][1]; rdml.org still lists CFX Maestro, LC96 and RGQ at 1.1 and MyGo at 1.2 [30]; RDML 1.4 is CR and rdmlpython 2.0 (which "introduced RDML v1.4" and Ncopy) is not on PyPI [31][32]; MIQE 2.0 requires raw data in RDES/RDML and efficiency-corrected quantities [37].
3. **What exists.** rdmlpython `load_any_zip`, RDML-Validate (schema only), RDML-Tools migration between versions, RDML-Ninja (2015). Nothing reports *what is missing for which analysis*, and nothing writes 1.4 `Ncopy` from a pip install.
4. **Feature.** `qpilot rdml inspect <file>` → a conformance report with named facts: container (zip/xml, inner name), declared version, per-run presence of `adp` (raw amplification points), `mdp` (melt), `cq`, `N0/ampEff` (1.3+), `Ncopy` (1.4), dye/sample/target metadata, pcrFormat, vendor namespace extras (LC96), dPCR partitions; a *dialect label* (e.g. "Bio-Rad CFX Maestro 1.x Cq-only", "LightCycler 96 1.1 (+Roche analysis)", "QuantStudio D&A 2.x 1.3") inferred from signatures; and a *fix plan* (repair inner name, migrate version, fall back to export recipe from Discovery 1). Writer: emit RDML 1.3 (REC) by default and 1.4 CR on request with `Ncopy`, `nCopyFact`, `vol`, `doubleStranded` populated from engine facts, plus an RDES TSV pair per run (spec in [31-RDES]) and the Analysis Record's decision log in `documentation` elements. Vendor rdmlpython from GitHub at a pinned commit (MIT) or re-implement the 1.4 validation against `RDML_v1_4_CR.xsd` (MIT). Agents get `qpcr_rdml_inspect` and `qpcr_export(format="rdml-1.3|rdml-1.4-cr|rdes|asm")`.
5. **Feasibility.** Schemas and change logs are MIT [31]; dialect fixtures exist under MIT/CC-BY (§4); effort ≈ 2 weeks for inspector + writer upgrades; hardest part: keeping dialect signatures current as vendors update (needs the public fixture corpus and a contribution path for users to donate anonymised files).
6. **Why qPilot.** The Analysis Record is already RDML; the conformance report becomes a Decision Card ("this plate's RDML has no raw points — results will be Cq-based; reviewer-visible"); Study Confidence can be driven by it.
7. **Risks.** RDML 1.4 may change before REC (write 1.3 by default); GPL contamination if RDML-Tools code is copied (do not; only rdmlpython/MIT). Confidence **high**.

### Discovery 3 — Allotrope ASM qPCR output with qPilot's calculated-data provenance, packaged in a licence-safe way

1. **Persona.** Biotech/pharma scientists whose data must land in Benchling, TetraScience or an ELN; data engineers who already consume ASM.
2. **Evidence.** Benchling's QuantStudio, D&A and CFX connectors produce ASM qPCR JSON on `REC/2024/09` and flatten it to well/measurement/group/datacube CSVs [42][41]; TetraScience lists QuantStudio integrations and promotes ASM generation [44]; ASM qPCR has data cubes for reporter, passive reference, normalized, baseline-corrected and melting-curve data [41-schema]; ASM versions are cut quarterly (2026/09 is current) [40-tree]; licence: CC BY-NC 4.0 for non-commercial use, CC BY-ND 4.0 for commercial use "restricts modifications", member licence for modification with Allotrope validation [40-lic]; README: REC models public, CR models member-only, "link to a specific version … for production" [40-readme].
3. **What exists.** allotropy (MIT) converts *vendor exports* to ASM but carries no analysis provenance; vendor tools do not emit ASM. No tool emits ASM *from* an open re-analysis with calculated-data lineage.
4. **Feature.** `qpilot export --asm` writes an ASM qPCR document pinned to a named REC version: per-well "reporter data cube" and "passive reference data cube" from the raw layers captured in Discovery 1 (true raw where available), "baseline corrected reporter data cube" from LinRegPCR's baseline, "processed data document" with qPilot's threshold/baseline settings, and a "calculated data aggregate document" whose entries ("N0", "PCR efficiency", "Ncopy", "normalised expression", "geNorm M") each carry `data source document` references to the measurement identifiers — the ASM-native form of qPilot's "no naked numbers" fact ids. Also `qpilot import --asm` (consume allotropy output so Benchling-connected labs can re-analyse). Packaging: do not copy the schema files into the Apache-2.0 tree; validate against a fetched, version-pinned schema (or make allotropy, MIT, an optional extra and note Allotrope's licence in NOTICE); the JSON documents themselves are the user's data.
5. **Feasibility.** Schema and sample files readable without membership [40]; allotropy's test JSON shows the exact key names [41-ex]; effort ≈ 1–2 weeks; hardest part: licence posture (seek a written clarification from Allotrope on whether producing conforming documents requires any licence; CC BY-ND covers redistribution of the schema, not documents) and keeping up with quarterly REC versions.
6. **Why qPilot.** The record already holds every number with provenance; ASM's calculated-data/data-source structure maps 1:1; the domain-agnostic core can reuse the same writer for plate-reader ASM later.
7. **Risks.** ASM licence ambiguity for an open-source project; integrators may still only read Cq columns (Benchling's CFX connector ignores melt/replicate data [42-CFX]). Confidence **medium-high**.

### Discovery 4 — Plate-layout round trip through vendor-native setup files, with a "what actually ran" check

1. **Persona.** Student or technician who designs the plate (randomised blocks, inter-plate calibrators — already on qPilot's roadmap) and then re-types it into the vendor software; core-facility manager who receives plates with wrong or missing sample names. Every plate.
2. **Evidence.** P10: Benchling's guides repeatedly instruct users to type sample names and a barcode/plate identifier by hand or import a "Sample Definition File" [42]; Thermo documents plate-setup `.txt`, sample `.txt`, barcode `.txt`, AIF files and precedence rules for `cmdlineutil -expgen` [1] and D&A 2 import/export of plate-setup files and OpenArray `OA.csv` [2]; Bio-Rad documents the `.plrn` CSV with required fields (PlateType, ScanMode, Units, RunProtocol, per-channel dyes, SampleType, per-standard quantities; 30-char RunID; 20-char well notes) and "GenerateLIMSPLRNfile" [9]; qPCRsoft imports a LIMS transfer file [22]; LightCycler PRO "synchronizing plate setups with host" [14]. The forum reports plates that need specific skirts/sealers for automation and LIMS merges [51].
3. **What exists.** LIMS vendors generate these files; most academic labs never see them; no open tool writes them from a design.
4. **Feature.** `qpilot plan` already proposes a layout; add `qpilot layout push --vendor thermo|biorad|jena` producing the documented artefacts: Thermo plate-setup `.txt` + sample `.txt` (+ `.edt` via `cmdlineutil -expgen` where D&A 1.2.x exists, or D&A 2 "Import a plate setup file"); Bio-Rad `.plrn` (Table 38 spec) with run protocol name; Analytik Jena LIMS transfer file. After the run, the capture from Discovery 1 reads back the plate setup embedded in `.eds`/`.rex`/RDML/exports and qPilot raises a Decision Card on any diff ("well C7: design says NTC, instrument says Unknown") before analysis; the design hash and the as-run layout both enter the record. Agents call `qpcr_layout_push` and `qpcr_layout_verify`.
5. **Feasibility.** Formats are documented in vendor guides [1][9][22]; D&A plate-setup export gives a reference example to round-trip; effort ≈ 1–2 weeks for Thermo + Bio-Rad; hardest part: field-length limits and vendor validation quirks (the CLA guide says to validate generated files by opening them in the desktop software).
6. **Why qPilot.** Closes the loop between `qpilot plan`, capture and the record; the "pipetted against the wrong layout" failure becomes machine-detectable.
7. **Risks.** Vendor file formats change silently (D&A 2 vs 1.x); limited to the vendors with documented import files. Confidence **medium-high**.

### Discovery 5 — Zero-click capture daemon, and a precise map of where GUI automation is truly needed

1. **Persona.** Core facilities and automated labs; students who forget to export.
2. **Evidence.** Auto-export exists on QuantStudio 6/7 Pro (export settings imported to the instrument; XLS/network drive) [2][42], CFX Maestro ("Automatically export LIMS data at end of run"; email `.pcrd`; Opus shared folder) [9][10], qPCRsoft (raw CSV + Ct CSV + `.ajq` zip) [22], LightCycler PRO (SFTP) [14], Cielo (email notifications) [25]; integrators all use watched folders [42]. Where auto-export does not exist or does not reach raw data: Bio-Rad retrospective `.pcrd`, Q-Rex/QIAquant (unknown), Mic (unknown), Biomark (Table export only), LC480 (manual text export; `.ixo` readable), LC PRO customer export format unknown.
3. **What exists.** Benchling Gateway, TetraScience file-log agents (commercial); FEUSION Extractor (GUI automation for Q-Rex, unlicensed); covmatic PCR_station (MIT; Maestro XML/USB handshake) [55][56].
4. **Feature.** A local `qpilot capture` daemon (watch folder / SFTP pull / instrument network share) that fingerprints files, applies the capture recipes, assembles studies by barcode/plate identifier, stores originals in the record and raises Import Trust Cards. Scope the GUI-automation fallback ("GhostDriver") narrowly and with evidence: Bio-Rad CFX Maestro (Export All Data Sheets / RDML for old `.pcrd`), Q-Rex and Mic Workbench (export formats unverified), Biomark Real-Time PCR Analysis (raw export unverified). Everything else is reachable by file or auto-export.
5. **Feasibility.** Watchers are trivial; the value is in the recipes and the record; effort ≈ 1 week for daemon + 1 week per GUI driver; hardest part: Windows instrument PCs with locked-down policies (CFX Maestro says instrument PCs must not auto-restart; Security Edition uses HASP keys) [9].
6. **Why qPilot.** Local-first by design; the record wants the originals; agents want a queue of trusted plates.
7. **Risks.** GUI automation is brittle across versions and may conflict with vendor EULAs (unread) — keep it opt-in and version-pinned. Confidence **medium**.

### Discovery 6 — Open qPCR (Chai) as the open reference instrument for a live-analysis and classroom mode

1. **Persona.** Teaching labs, DIY-bio and method developers who want the engine to see curves during a run.
2. **Evidence.** P5: every major vendor gates instrument APIs (Thermo "exclusive to authorized OEM partners" [5]; no Bio-Rad/Roche/Qiagen API found; SiLA has no qPCR driver [46]); Chai's software is Apache-2.0 with documented endpoints returning per-cycle raw, background- and baseline-subtracted values and `dr1/dr2` predictions, plus a zip export [28-ctrl]; hardware CC BY 4.0 [29].
3. **What exists.** Chai's own web UI; nothing open consumes its API for LinRegPCR-style decisions.
4. **Feature.** `qpilot live --chai http://openqpcr.local` polling `amplification_data?raw=true` during a run, running the engine incrementally, and surfacing early Decision Cards (NTC amplifying, reference gene unstable) before the run ends; the classroom worksheet uses it as the only instrument students can inspect end-to-end.
5. **Feasibility.** API documented in source; a device costs money (unverified price); effort ≈ 1 week. Hardest part: polling semantics (202/503 job states) [28-ctrl].
6. **Why qPilot.** Demonstrates the closed-loop contract with a real instrument without OEM gates.
7. **Risks.** Niche hardware; limited to 16-well Open qPCR. Confidence **medium** (value), **high** (feasibility).
