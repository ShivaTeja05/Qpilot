# qPilot threat model (one page)

qPilot is local research software. It reads a qPCR export (RDML), analyses it deterministically, shows the scientist the choices that can change a conclusion, records their decisions, and offers the same functions to AI agents over MCP (stdio). The scientist uses it through **one page**: `qpilot app` starts one local server (FastAPI, on `127.0.0.1`) that serves the page, its JSON API and a live event stream, over the same on-disk store the MCP server writes. It is **not** for clinical or diagnostic use and is **not** a multi-user service.

## Assets
| Asset | Why it matters |
|---|---|
| Raw curves and sample/target names in the input file | May be unpublished or patient-derived |
| The decision log (`decisions.jsonl`) and the Analysis Record | The evidence of who chose what and why |
| The Studio inbox (`sessions/<input_sha256>/proposals.jsonl`) | What the AI proposed and what a person accepted; the engine builds its design from accepted proposals only |
| The pseudonym key (`sessions/<input_sha256>/.keys/hmac.key`) | Whoever holds it can confirm a guessed sample name behind a token |
| The numbers (`results.json`, `facts.json`) | What a paper or a reviewer relies on |
| An API key for a frontier model (if used) | Spending and account access |
| The launch key (`/?token=…` link, the `qpilot_token` cookie) | Whoever holds it can use the page's API for as long as that launch runs, including making the decisions only a person may make |
| Uploaded input files (`studio-inputs/` next to the study store) and the launch's private export folder | Unpublished or patient-derived data, kept on disk so a session finds its file again after a restart |
| The user's filesystem | An agent, a web page or an uploaded file must not be able to read arbitrary files through qPilot |

## Trust boundaries
```
RDML file (untrusted) ─▶ io (hardened loader) ─▶ engine (qpcr + core, no network, no model)
                                                      │
                                                      ▼
                                        core/store.py: the only writer to a workspace
                                       ┌──────────────┼───────────────────────────┐
                                       ▼              ▼                           ▼
                   the one server on 127.0.0.1    MCP server (stdio)       ai/ → model endpoint
                   (the scientist's browser)      (any agent; untrusted)   (only if chosen)
                   Guard: Host · launch key ·
                   same-origin writes · headers
                   → page · /api · /api/events
```
**Untrusted inputs:** RDML content (including names inside it), sample sheets, every MCP tool argument (including every field of a proposal), every model output, a record zip received from someone else, and every HTTP request to the server (its `Host`, `Origin` and `Referer` headers, query strings, JSON bodies, uploaded files and their file names). A request from the user's own page is trusted only as far as the launch key and the same-origin check go (rows 13 and 24); what it asks for is still checked by the same code the command line and the MCP server use.

## Open findings of the review of the one server
The red-team review keeps every finding it has demonstrated and the owner has not yet fixed as a strict-`xfail` test in `tests/web/test_redteam_*.py`, named `RT-UI-nnn`. When an owner fixes one, the test becomes an ordinary regression test and its line leaves this list. Open on 20 Oct 2026:

| Id | Finding | What it could do |
|---|---|---|
| RT-UI-001 | The redirect after a valid key copies the request path into `Location` (`//host/?token=…`) | Send a browser that holds the right key to another site (it needs a valid key to start) |
| RT-UI-002 | The launch-key cookie has the same name on every port | A second launch overwrites the first tab's key; another local web server in the same browser is sent the key (row 24) |
| RT-UI-003 | `Guard` passes non-HTTP connections (WebSocket) straight to the app | The server has no WebSocket route today; one added later would be unguarded |
| RT-UI-004 | The upload cap reads only `Content-Length` | A chunked body is spooled to temporary storage before it is refused (row 29) |
| RT-UI-005 | A NUL byte in a static path raises an error | A 500 answer and a traceback in the terminal instead of a 404 (row 26) |
| RT-UI-006 | Every `open` job has the same key, so jobs are shared | A second, different file dropped while the first is opening is not opened |
| RT-UI-007 | The job list evicts the oldest job even while it runs | Its id answers 404 and the same work can start twice (row 28) |
| RT-UI-008 | The store watcher opens `results.json` without checking it is a regular file | A named pipe there stops live updates (row 27) |
| RT-UI-010 | The open job names the kept copy, not the dropped file | A hash-like name in the message |
| RT-UI-011 | One damaged `results.json` makes the workspace list fail | The Open page lists nothing |
| RT-UI-012 | A session whose `source.json` names a named pipe hangs the workspace list | Listing holds a worker thread |

None of these lets a web page in the browser get past the Host check, the launch key or the same-origin rule today: RT-UI-001 starts only from a request that already carries the right key, and RT-UI-003 concerns a kind of route the server does not have. The rest need the key, or damage to the study store on this computer.

## Out of scope
A compromised host or Python environment; another program running as the user that can read the terminal, the browser's cookies or a process's memory (it can use the launch key, row 24); a malicious lab profile written by the user themself; proving who authored a record (signatures are roadmap); multi-user hosting, accounts and roles; 21 CFR Part 11; clinical or diagnostic use.
