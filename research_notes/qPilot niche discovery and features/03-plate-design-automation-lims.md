# 03 — Before the plate goes on the instrument: plate design, randomisation, inter-plate calibration, liquid handlers, instrument plate-setup imports, barcodes, LIMS/ELN

Researcher notes for the qPilot niche-discovery effort. Date: 17 October 2026. Scope: everything between "I have cDNA and primers" and "the instrument starts cycling", plus the hand-offs from that stage into analysis and into the lab's record systems.

Method note (read first): roughly 45 web searches were run before the session's shared search budget was exhausted; after that, all evidence came from direct fetches of primary pages (vendor manuals, API specs, GitHub/CRAN/PyPI, papers) and from local text extraction of four vendor PDFs (Bio-Rad CFX Maestro 2.3 User Guide, Bio-Rad CFX Maestro API Reference, Thermo QuantStudio Design & Analysis v2 Desktop User Guide, EPFL GECF Hamilton qPCR guide). ResearchGate, Reddit, Biology StackExchange, Benchling's help centre, Hamilton's site and the Opentrons community forum could not be fetched (403 / DNS / blocked), so forum evidence from those sites is limited to what search snippets returned and is labelled "(search snippet)". Everything else is from the fetched page or PDF itself.

Terms used below (for the two developers):
- **Plate map / plate layout / plate setup**: the table that says which sample, which target (primer pair or assay), which task (unknown, standard, no-template control...) and which dyes sit in which well (A1...P24).
- **Worklist**: a robot's list of transfers (source well → destination well, volume, liquid class).
- **NTC / NRT**: no-template control (water instead of cDNA) / no-reverse-transcriptase control (RNA that was never reverse-transcribed; detects genomic DNA).
- **IRC / IPC**: inter-run (inter-plate) calibrator: the same sample run on every plate so plates can be scaled onto one another.
- **Cq, E, N0**: quantification cycle; PCR efficiency; starting target quantity (N0 = Nq / E^Cq, where Nq is the fluorescence threshold).
- **Sample maximisation vs gene maximisation**: put all samples for one gene on one plate (so plates never need calibrating for that gene) vs put all genes for some samples on one plate (needs calibrators).
- **LIMS / ELN**: laboratory information management system (samples, plates, barcodes, results) / electronic lab notebook (experiments, protocols, files).
- **ANSI/SLAS**: the microplate footprint and well-position standards every 96/384 plate follows.
- **SiLA 2, Allotrope ASM, RDML, .eln**: lab-automation device-communication standard; instrument-data JSON schemas; the qPCR data XML standard qPilot already uses; the ELN-exchange zip format (RO-Crate).

## 1. How this corner of the niche works

### 1.0 The chain, hop by hop (what actually happens today)

A multi-plate qPCR study passes through four representations of "which well holds what", and today each one is re-typed or re-imported by hand:

1. **Design** (Excel template, vendor plate editor, or an R/Python script). A typical lab SOP: "plan the layout in the lab's Excel template (qpcr_plate_setup.xlsx), then print it", then mark completed wells on the printout with a Sharpie while pipetting [33].
2. **Pipetting** (by hand from the printout, or by a robot fed with a separate file). At EPFL's gene-expression core facility the user fills two Excel sheets named exactly "DNA" and "PRIMER" (".xls, not .xlsx"), a Hamilton "PCR GUI" running inside a VMware Windows XP virtual machine generates the assay×sample matrix and worklist, and "the robot outputs a .txt file. This file can be loaded in the qPCR instrument, filling in automatically samples positions, detectors, dyes and standard curve quantities" [15].
3. **Instrument plate setup** (QuantStudio Design & Analysis import of a TXT/CSV that "overwrites all existing settings" [7][8][9]; Bio-Rad CFX Maestro spreadsheet import or a LIMS `.plrn` file [12]; Roche LightCycler 480 Sample Editor text import [16][17][18]).
4. **Analysis layout** (the exported results carry the names that were typed at step 3; the analyst re-matches them to the design, and this is where threads such as "I am having trouble importing data to HTqPCR ... it feels as if I am missing a simple solution" come from [19]).

Every hop has its own file format, its own naming rules (exact case, unique names, one sample per well, no apostrophes) and no shared identifier, which is why layouts drift out of sync. The rest of Section 1 answers the six key questions with cited findings.

### 1.1 Key question 1 — How are layouts designed today, and what goes wrong?

#### Takeaway
Layouts are designed in Excel templates, in the vendor's plate editor, or (rarely) with R packages; the only randomiser found is GPL-2 and has 4 stars. The documented failure modes are destructive/strict instrument imports, name mismatches between files, replicates or samples spread across plates without calibrators, fragile legacy robot software, and evaporation/position effects for which qPCR-specific evidence is thin.

#### Cited Findings
- Design in Excel + print + Sharpie is a published lab SOP: "Plan the layout in the lab's Excel template (qpcr_plate_setup.xlsx), then print it ... important with large plates"; "Mark the plate with a Sharpie and track completed wells against the printout" — [Barrick lab QPCR SOP](https://barricklab.org/twiki/bin/view/Lab/QPCR) [33].
- Vendor editors are the second design tool. Thermo's workflow: export the plate setup as CSV, fill in Sample Name, Target Name, Task (usually UNKNOWN), Reporter, Quencher for used wells, "Leave the rest of the plate blank", re-import under Actions > Import plate setup, then "Check the visual representation of your plate layout and make sure it is correct" — [Bridges Lab protocol](https://bridgeslab.sph.umich.edu/protocols/index.php?title=Set_up_qPCR_Run_on_Thermo_Cloud_and_QuantStudio) [11].
- Thermo's import is destructive and strict: "Click OK to confirm that the plate setup is overwritten"; "Each sample name in the Samples table must be unique. Do not add multiple entries for technical replicates"; "Each well can contain only one sample"; pasted Excel "Column headers must match the column headers in the Samples table" — [QuantStudio D&A v2 Desktop UG, MAN0018200](https://documents.thermofisher.com/TFS-Assets/LSG/manuals/MAN0018200_QuantStDesgnAnalysisSW_v2_Desktop_UG.pdf) [9]. Names "must match ... exactly (including case)" and "the rows can occur in any order, but the location information (in columns 1 and 2) must be accurate" — [Thermo plate setup files help](https://apps.thermofisher.com/apps/help/MAN0014303/GUID-6F7D8B38-680C-496A-968C-700658A8F05A.html) [7].
- Thermo template (.edt) and data (.eds) files are "checksum protected. This helps to ensure that they are not edited outside of the system" — [9]. So a third-party tool cannot write a plate file directly; it must go through the TXT/CSV import.
- R tools: tidyqpcr (Apache-2.0) builds plans by copying a small block across the plate so that "technical replicates of the same sample are not in adjacent wells", but it does not randomise and "cannot separately detect row- or column-specific artefacts" — [tidyqpcr plate-setup vignette](https://docs.ropensci.org/tidyqpcr/articles/platesetup_vignette.html) [29]. plater (CRAN 1.0.5, 2024-10-25) is GPL-3 and only reads/displays plate-shaped data — [CRAN](https://cran.r-project.org/web/packages/plater/index.html) [30]. crukci-bioinformatics/PlateLayout ("Plate Layout Randomiser" 0.3.3, 2023-02-27) is GPL-2, 4 stars, pseudo-block randomisation with a 1/distance score for same-group neighbours — [GitHub](https://github.com/crukci-bioinformatics/PlateLayout) [28].
- wellmap (MIT, 27 stars, v3.5.2 Sept 2023; Kundert 2021 BMC Res Notes 14:164) is a TOML plate-layout file format with Python and R parsers — [GitHub](https://github.com/kalekundert/wellmap), [PyPI](https://pypi.org/project/wellmap/) [31].
- Automatic Genomics (BioTechniques 2011, DOI 10.2144/000113574) was an Excel/VBA tool that designed 384-well qPCR plates and generated Tecan Freedom EVO loading commands — [tandfonline](https://www.tandfonline.com/doi/full/10.2144/000113574) (search snippet; full text 403) [32].
- A free web designer (Conduct Science) exports CSV/JSON (well, row, column, condition) and advises: "Outer wells (especially corners) lose more volume to evaporation" and "randomize sample positions and include plate position as a covariate in analysis"; it does not randomise automatically — [Conduct Science](https://conductscience.com/tools/96-well-plate-map-generator) [27].
- Evidence on position effects: in 96-well cell culture plates outer wells showed ~16–35% lower metabolic activity than central wells, partly mitigated by loosely sealed wrapping — [PMC8024881](https://pmc.ncbi.nlm.nih.gov/articles/PMC8024881/) [25]. For qPCR specifically a ResearchGate thread reports position effects are uncommon on modern instruments and that poor sealing/evaporation is the usual cause (search snippet) — [ResearchGate](https://www.researchgate.net/post/Is-there-an-effect-of-well-position-on-ct-in-qPCR) [23]. A plate vendor blog claims "60% of reported evaporation-related issues in 96-well plates occur in the outer wells" (marketing source) — [Thomas Scientific](https://www.thomassci.com/blog/_/why-your-qpcr-data-might-be-misleading) [26]. PlateVision (CRAN) sells itself on heatmaps "allowing users to instantly detect pipetting errors, edge effects, and outliers" — [CRAN](https://cran.nics.utk.edu/cran/web/packages/PlateVision/index.html) [72].
- Name/format mismatch pain: LightCycler 480 export rejected by CopyCaller as "not a compatible file" (search snippet) — [ResearchGate](https://www.researchgate.net/post/How-to-import-txt-from-LightCycler-480-into-CopyCaller-software) [24]; pyQPCR: "The file XXX.txt does not contain any well at the right format" because the export had raw fluorescence, not Cq — [SourceForge](https://sourceforge.net/p/pyqpcr/discussion/918935/thread/51521e89/) [20]; a commercial miRNA assay note stresses that sample names in run .txt files must exactly match a separate metadata file (search snippet) — [osteomiR TN-02](https://www.tamirna.com/wp-content/uploads/2019/09/161204_TN02_technote_Software.pdf) [71].
- Legacy robot fragility at a core facility: lists with empty rows "will crash the software later"; "'" (apostrophe) "is not supported and may cause the robot to skip samples/assays"; the Hamilton PCR GUI runs "through a virtual machine (VMWare)" on Windows XP after the host moved to Windows 10 — [EPFL GECF guide v5.03](https://www.epfl.ch/research/facilities/gene-expression-core-facility/wp-content/uploads/2021/04/qPCR-plate-setup-guide-with-Hamilton-MicroLab-Star-v5.03.pdf) [15].

#### Inferences
- The de-facto "plate map" is a spreadsheet with no identifiers, and every downstream system validates names rather than IDs; mismatches are therefore detected (if at all) only after the run, by the analyst.
- Nobody ships a permissive, maintained randomiser/designer for qPCR; the R ones are GPL and the web one is manual. This is a genuine gap qPilot can fill without licence conflict by implementing from the published descriptions.
- Edge effects are a real but second-order concern in qPCR (sealing dominates); the design assistant should treat edge wells as a soft rule (keep NTCs/IRCs and critical replicates off corners), not a hard one.

#### Gaps
- No peer-reviewed study of well-position effect on Cq for modern 384-well blocks was found (searches returned cell-culture work and vendor claims).
- Reddit r/labrats threads on mis-pipetted layouts could not be retrieved (search returned none; site not fetchable afterwards).
- PlateEditor (Pasquier) could not be located after the search budget ended; its licence and status are unverified.

### 1.2 Key question 2 — Design methods: sample maximisation, IRCs, factor correction, nested variance, randomised blocks

#### Takeaway
Three published, deterministic methods cover multi-plate design and correction: Hellemans 2007 (sample maximisation; IRC geometric-mean calibration with error propagation), Ruijter 2015 (factor correction from all overlapping replicates, no calibrators needed, with explicit design-completeness rules), and Kitchen/Kubista/Tichopad 2010 (nested variance components from a pilot to allocate replicates). Only qbase+ (commercial), qRAT (MIT; IPC only) and Factor-qPCR (closed, Excel/RDML) implement any of them; none checks a layout before pipetting.

#### Cited Findings
- Hellemans 2007: "the sample maximization method is highly recommended" because run-to-run variation is "often underestimated"; IRCs are "identical samples that are tested in both runs"; "A failed calibrator does not ruin an experiment if two or more are available"; using three IRCs cut the error increase from ~70% (one IRC) to ~40%; the calibration factor is the geometric mean of the IRCs' normalised relative quantities, per gene, after normalisation; the formulas "can only be used for inter-run calibration if the same set of IRCs is used in all runs"; calibrating on NRQs means "independently prepared cDNA of the same RNA source can be used as a calibrator in the different runs", whereas calibrating on Cq requires the same template dilution in all runs; without shared-gene measurements "qBase cannot calibrate and assumes no inter-run difference" — [Hellemans et al. 2007, Genome Biology 8:R19](https://pmc.ncbi.nlm.nih.gov/articles/PMC1852402/) [1].
- Ruijter 2015 (Biomol Detect Quantif 5:10–14): plate differences are multiplicative; for each plate pair take the geometric mean of ratios of observations of the same *condition* (unique target × treatment × biological variable); missing pairs are filled by nested geometric means (Eq. 3); each plate factor is the geometric mean of its column in the completed ratio matrix (Eq. 4); divide every N0 by its plate factor (Eq. 5); convert back to an efficiency-corrected Cq with threshold 1 (Eq. 12) using a per-target mean efficiency weighted by reactions per plate (Eq. 8). Design rules: "maximum overlap between plates with respect to targets and samples"; "The design of the experiment should preferably be balanced and complete"; "when more than 2 rounds of substitution are required, the design of the experiment is clearly incomplete" (recommendation: run another plate); "the required overlap is not restricted to such technical replicates". Critique of calibrators: missing calibrator values bias the factor, calibrator error propagates to every sample on the plate, and calibrators cannot be reused in later statistics. Example dataset: chicken heart, 4 genes × 5 regions × 6 plates, with runs 2 and 5 differing ~6-fold — [PMC4822202](https://pmc.ncbi.nlm.nih.gov/articles/PMC4822202) [2].
- The RDML-aware Factor-qPCR program "completes the analysis pipeline" raw data → LinRegPCR → Factor Correction → qbase+, storing corrected N0 as "efficiency-corrected Cq values"; authors Ruijter, Hellemans, Ruiz-Villalba, van den Hoff, Untergasser (qPCR & NGS, Freising 2015) — [econferences.de](https://www.econferences.de/removal-of-between-plate-variation-in-qpcr-with-factor-correction-completion-of-the-analysis-pipeline-supported-by-rdml/) [3].
- Correction must be on quantities, not Cq: "some methods are erroneously based on dividing the Cq values on a plate by a factor per plate" (search snippet of Ruijter et al. 2021, Life 11:496) — [MDPI](https://www.mdpi.com/2075-1729/11/6/496) [68].
- Kitchen, Kubista, Tichopad 2010 (Methods 50:231–236, DOI 10.1016/j.ymeth.2010.01.025): "estimation of expected variances and treatment effect magnitude is often uninformed and unreliable"; the method uses "a small pilot study to estimate the biological and technical variances" and "a software implementation of these methods, powerNest" that predicts variance and power and suggests an optimal nested design — [ASEP record](https://asep.lib.cas.cz/arl-cav/en/detail-cav_un_epca-0350829-Statistical-aspects-of-quantitative-realtime-PCR-experiment-design), [gene-quantification.de summary](https://gene-quantification.de/bioinf-subpage3.html) [4].
- qRAT (2022, MIT): "it is necessary to include one common sample in all runs/plates per common sample-set"; IPC via geometric mean of IPC Cq per plate scaled to the cross-plate mean; the authors prefer sample maximisation since "all samples must be analysed for a given gene in the same run" — [PMC9297597](https://pmc.ncbi.nlm.nih.gov/articles/PMC9297597/) [6].
- MIQE 2.0 (Bustin et al. 2025, Clin Chem 71:634): NTC amplification "could indicate reagent contamination or cross-contamination between samples" and "results from the entire run may be invalidated"; "it is necessary to include a no-RT control"; a sample counts as positive only if "its Cq precedes that of the negative control by at least 5 cycles"; authors must state "Whether thresholds are consistent across runs or determined individually for each run"; standard curves need "a minimum of 3 technical replicates for each step"; checklist asks for "Frequency and Cq of negative controls", "Description of replicates", "Repeatability", "Reproducibility", RDES/RDML raw-data submission — [OUP](https://academic.oup.com/clinchem/article/71/6/634/8119148) [5].
- Pseudo-block randomisation as implemented in PlateLayout: groups ordered randomly, assigned by traversing the plate diagonally, rows and columns shuffled as blocks, repeated many times and scored by Σ 1/distance to same-type samples within distance 2 — [GitHub](https://github.com/crukci-bioinformatics/PlateLayout) [28].
- Forum reality (search snippets): "What is the best way to combine biological replicates from different qPCR plates?" and "QPCR: analyses involving in-between plates?" — answers suggest using a sample that happened to be on both plates as the calibrator, otherwise "I would have some doubt in the convenience in combining data from different plates", and "simple side-by-side boxplots by plate will give you an idea of how much between-plate variation is there" — [ResearchGate](https://www.researchgate.net/post/What-is-the-best-way-to-combine-biological-replicates-from-different-qPCR-plates), [ResearchGate](https://www.researchgate.net/post/QPCR-analyses-involving-in-between-plates) [21][22].
- Core-facility rule of thumb: "When your experimental design requires multiple qPCR plates, keep all the samples on the same plate and dispatch assays on different plates (=aka 'sample maximization')" — [EPFL GECF](https://www.epfl.ch/research/facilities/gene-expression-core-facility/wp-content/uploads/2021/04/qPCR-plate-setup-guide-with-Hamilton-MicroLab-Star-v5.03.pdf) [15].

#### Inferences
- A design assistant needs as inputs: samples (with group, batch factors such as extraction date), targets (with reference/target flag), replicate counts, plate format, which controls per plate, and a plan for overlap (sample-maximise where possible; else IRC set ≥3 or a balanced overlap design). Outputs: per-plate layouts, the overlap graph between plates, the expected calibration method, and the files for each downstream system.
- The Ruijter completeness rule ("≤ 2 substitution rounds") and the Hellemans IRC rule ("same IRC set on every run; ≥2–3 IRCs") are both checkable from a layout before any pipetting, i.e. "design-time detection of layouts that cannot be analysed" is a mechanical computation.
- Because qPilot already computes per-well efficiency and N0 from raw curves, factor correction is a few-day addition and fits the robustness grid as an axis ("plate correction: none / IRC / factor").

#### Gaps
- Tichopad et al. 2009 (Clin Chem) variance-component numbers (sampling vs RT vs qPCR) could not be fetched (OUP/PubMed/EuropePMC blocked).
- Factor-qPCR software licence and current availability (hfrc.nl) not verified.
- No published study quantifying how often multi-plate designs lack calibrators was found; the frequency claim rests on forum threads and the fact that both qRAT and qbase+ document the requirement.

### 1.3 Key question 3 — Liquid handlers used for qPCR setup: formats and APIs; can one plate map drive robot and instrument?

#### Takeaway
Each robot family has a different, well-documented input: Opentrons (Python Protocol API with a single CSV "runtime parameter" since API 2.20, plus an HTTP API on the robot), Tecan (`.gwl` worklist records A/D/W separated by semicolons, or CSV converted to GWL), Hamilton (CSV/Excel worklists consumed by vendor methods; at EPFL an Excel pair through a legacy GUI), Integra VIALAB (GUI, worklist import), Formulatrix Mantis (CSV dispense templates, reagent-only). PyLabRobot (MIT) abstracts Hamilton STAR/Vantage, Tecan EVO and Opentrons OT-2 in Python. Today the robot's output is at best a `.txt` to hand-load into the instrument; no tool emits both the robot file and the instrument's plate-setup file from one object.

#### Cited Findings
- Opentrons runtime parameters: `add_csv_file` (API 2.20) alongside `add_bool/int/float/str` (2.18); "Only one CSV parameter is allowed per protocol"; "CSV parameters have no default value"; in the App the technician "can choose any file on their computer", on the Flex touchscreen from USB — [Opentrons docs: defining](https://docs.opentrons.com/python-api/runtime-parameters/defining/) [34]. `protocol.params.<name>.parse_as_csv()` returns rows (header first); accessing it "blocks protocol analysis until a CSV is selected", with a `RuntimeParameterRequiredError` try/except workaround — [Opentrons docs: using values](https://docs.opentrons.com/python-api/runtime-parameters/using-values/) [35].
- Opentrons' RT-PCR application page lists three open protocols: "qRT-PCR Prep with CSV File", "BioGX XFree RT-PCR Reaction Setup", "qRT-PCR Custom Reaction Setup", for OT-2 and Flex; no numbers on time saved — [Opentrons](https://opentrons.com/applications/rt-pcr-protocol) [36]. Its PCR-prep article describes a "super-mastermix" (mastermix + primers in one reservoir so each reaction needs one tip), bulk-dispense then samples, Temperature Module at 4 °C, and only qualitative "hours" saved — [Opentrons](https://opentrons.com/archives/resource/automating-pcr-prep-on-a-budget) [37]. Public protocols live in the GitHub repo that feeds the library — [Opentrons/Protocols](https://github.com/Opentrons/Protocols) [38] (directory names are hashed IDs, so qPCR protocols could not be enumerated from the listing).
- Opentrons robot-server is "the webservice that runs the Opentrons Flex and Opentrons OT-2" with endpoints for "executing protocols, controlling the hardware" — [robot-server README](https://raw.githubusercontent.com/Opentrons/opentrons/edge/robot-server/README.rst) [39]. Third-party wrappers describe port 31950, header `Opentrons-Version`, the OpenAPI spec served at `/openapi.json` and `/redoc`, uploading `.py`/`.json` protocols, creating a run from a protocol ID, and play/pause/stop actions (search snippet) — [labmcp-opentrons](https://socket.dev/pypi/package/labmcp-opentrons), [Opentrons MCP server](https://glama.ai/mcp/servers/aqfzeys0p7) [40]. The exact paths (`POST /protocols`, `POST /dataFiles`, `POST /runs`, `POST /runs/{id}/actions`) are from my own knowledge and must be verified against a robot's `/redoc`.
- PyLabRobot: licence file begins "MIT License" — [LICENSE](https://raw.githubusercontent.com/PyLabRobot/pylabrobot/main/LICENSE) [41]. README lists Hamilton STAR, Hamilton Vantage, Tecan Freedom EVO, Opentrons OT-2 backends; plate readers (CLARIOstar, Cytation5); Inheco ThermoShake; centrifuges; decks loaded from JSON (`Deck.load_from_json_file("hamilton-layout.json")`); atomic async commands (`pick_up_tips`, `aspirate`, `dispense`); a `run_pcr_profile` thermocycler call; a browser visualiser usable without hardware; citation Wierenga et al., Device 1(4):100111, 2023 — [README](https://raw.githubusercontent.com/PyLabRobot/pylabrobot/main/README.md) [41][42]. (The README did not mention Opentrons Flex.)
- Tecan: a worklist has seven record types (Aspirate, Dispense, Wash/Replace DiTis, Flush, Break, Set DiTi Type, Comment); "Each record starts with a single character ... followed by one or more parameters, separated by semicolons"; FluentControl's Convert CSV to GWL maps CSV columns to volume/source labware; "Mixed tip configurations ... are not allowed in the same Worklist"; well IDs are numeric unless "GWL File Uses Well Index Numbers" is unchecked (then A1...H12) — [Tecan FluentControl](https://www.tecan.com/knowledge-portal/how-to-use-worklist-in-fluentcontrol) [43]. EVOware "uses well positions 1-96 rather than the A1-H12 convention"; multi-pipetting "is possible when a worklist is written manually, but not when data is imported from a .csv file" — [Tecan EVOware](https://www.tecan.com/knowledge-portal/how-to-use-a-worklist-on-freedom-evoware) [44]. robotools (Python, writes EVO/Fluent GWL) is AGPL-3.0, 18 stars — [GitHub](https://github.com/JuBiotech/robotools) [45] (not usable in the distribution).
- Hamilton: EPFL's method takes .xls sheets "DNA" and "PRIMER" with task STND/NTC/UNKN and quantity ("Commas/dots are not supported, therefore multiply by 1000 if needed"), reporter/quencher per assay ("the dyes must be set correctly as the instrument only records corresponding wavelengths"), limits "Maximum number of primers couples is 64. Maximum number of DNA samples is 192", 3 replicates recommended, "A full 384w assembly takes approximately 30 minutes", reaction volume 10 µL (384) / 15 µL (96), and the output .txt is loaded into QuantStudio instruments — [EPFL GECF v5.03](https://www.epfl.ch/research/facilities/gene-expression-core-facility/wp-content/uploads/2021/04/qPCR-plate-setup-guide-with-Hamilton-MicroLab-Star-v5.03.pdf) [15]. A generic Hamilton worklist guide says to "ensure that the standard separator for lists is a comma and the decimal symbol is a period" and save as CSV (search snippet) — [TeselaGen](https://docs.teselagen.com/en/articles/3800012-hamilton-worklist) [46]. Hamilton's own PCR-setup page could not be fetched (403) [47].
- Integra ASSIST PLUS: VIALAB GUI protocols, "Importing worklists to VIALAB" (hit picking), ANSI/SLAS plates 12–384 wells, 384-well PCR cooling block, master-mix prep listed; no API or price — [Integra](https://www.integra-biosciences.com/global/en/pipetting-robots/assist-plus) [48]. Integra's WELLJET dispenser "supports API commands based on SiLA 2" (search snippet) — [Integra story](https://www.integra-biosciences.com/japan/en/stories/expanding-automation-reagent-dispensing-sila-2-integration) [51].
- Formulatrix Mantis: reagent dispenser (chip-based, tipless), "any SBS template from 6 to 1536 well plates", 2 µL qPCR reactions, CSV template import, "automation friendly", no API named — [Formulatrix](https://formulatrix.com/liquid-handling-systems/mantis-liquid-handler/) [49].
- SiLA 2: sila_base ("SiLA 2 Feature Definitions, framework protos and Schema") and sila_python are MIT — [GitLab sila_base](https://gitlab.com/SiLA2/sila_base), [GitLab sila_python](https://gitlab.com/SiLA2/sila_python) [50]. Members shown include Roche, Tecan, Novartis, Promega, Biosero — [sila-standard.com](https://sila-standard.com/) [50]. A 2025 open-source 4-channel peristaltic pump ships a SiLA 2 interface (~280 USD) (search snippet) — [FAU](https://open.fau.de/items/20363a4d-db67-4c9a-a65a-e31a76656ad2/full) [52]. No SiLA 2 driver for a qPCR instrument or a mainstream liquid handler was found.
- Protocol-language standards: LabOP (MIT, 52 stars) models protocols as OWL/RDF with `PlateCoordinates` (e.g. `A2:D2`) and sample arrays, executes via "BehaviorSpecialization" to equipment, has a Strateos/Autoprotocol integration and an Opentrons toy protocol — [GitHub](https://github.com/Bioprotocols/labop) [66]. Autoprotocol's site could not be fetched (expired certificate) [67].
- Bio-Rad's CFX Maestro side of the chain: the LIMS `.plrn` CSV has a "RunID" field "Enter short description or barcode identifying this run (30-character maximum, commas not allowed)" and the API's `RunID` is "Typically populated with the plate barcode" — [CFX Maestro UG 2.3](https://www.bio-rad.com/sites/default/files/webroot/web/pdf/lsr/literature/10000126764.pdf), [CFX API Reference](https://www.bio-rad.com/sites/default/files/2021-12/10000132623.pdf) [12][13].

#### Inferences
- Yes, one plate map can be pushed to both robot and instrument, but only by generating three artefacts from it (robot CSV/GWL/Python, instrument TXT/CSV/.plrn, analysis layout) and only if the generator owns the naming rules of each target. Nobody found does this; EPFL's robot→instrument `.txt` is the closest and is one-directional and vendor-specific.
- Opentrons is the easiest closed loop (Python + CSV runtime parameter + HTTP API, all documented, permissive tooling); PyLabRobot (MIT) is the route to Hamilton/Tecan without touching VENUS/FluentControl licences; Tecan GWL is trivial to emit from Python (no library needed; robotools is AGPL so write ~50 lines instead).
- Robots care about *source* positions (tube racks) and volumes, instruments care about *destination* names and dyes; the shared object must hold both, keyed by a stable sample ID, not by name.

#### Gaps
- The CSV column convention of Opentrons' "qRT-PCR Prep with CSV File" protocol could not be read (library site is JS-rendered; repo directories are hashed).
- Hamilton VENUS worklist file format and Beckman Biomek, Eppendorf epMotion, SPT Labtech mosquito/dragonfly, Andrew+ (Waters OneLab) formats were not reached before the search budget ended; treat as unverified.

### 1.6 Key question 6 — Standards, barcodes and sample-tracking failures

#### Takeaway
Plate geometry is fixed by ANSI/SLAS 1-2004 (footprint) and 4-2004 (well positions); instrument data has two overlapping standards (RDML, which qPilot already uses and which carries plate format and IRC flags; Allotrope ASM qPCR, JSON, whose schemas are CC BY-NC); device control has SiLA 2 (MIT reference code). Barcodes appear as fields in CFX `.plrn`/API ("RunID ... plate barcode") and Benchling (registry-unique plate/container barcodes). Quantitative evidence on sample mix-up rates was not reachable after the search budget ended.

#### Cited Findings
- ANSI/SLAS 1-2004 (footprint), 2-2004 (height), 3-2004 (flange), 4-2004 (well positions, R2012), 6-2012 (well bottom elevation), maintained by the SLAS Microplate Standards Advisory Committee; 96-well footprint 127.76 × 85.48 mm — [SLAS](https://www.slas.org/education/ansi-slas-microplate-standards/), [ANSI/SLAS 4-2004 PDF](https://www.slas.org/SLAS/assets/File/public/standards/ANSI_SLAS_4-2004_WellPositions.pdf) [53].
- RDML: versions 1.0–1.3 listed on rdml.org; rdmlpython validates against schemas including `RDML_v1_4_CR.xsd` (a 1.4 candidate exists) — [rdml.org](https://rdml.org/), [rdml.py source](https://raw.githubusercontent.com/RDML-consortium/rdmlpython/master/rdml.py) [65]. In the source: run-level `pcrFormat` has children `rows`, `columns`, `rowLabel`, `columnLabel` ("96-well plate; A1-H12" → 8×12, "384-well plate; A1-P24" → 16×24, "free format" → rows −1); react ids are numeric, computed as `number + letter_index * columns` (A=0, number 1-based; B3 on a 96-plate = 15); sample child elements include `interRunCalibrator`, `calibratorSample`, `quantity`, and `type` defaults to `"unkn"`; no function converts a react id back to "A1" — [rdml.py](https://raw.githubusercontent.com/RDML-consortium/rdmlpython/master/rdml.py) [65]. RDML-Tools (Untergasser) include RDML-Edit, RDML-AnnotationEdit (sample annotations), RDES-TableShaper ("Reshapes a table in RDES format for import into RDML"), RDML-Merge, RDML-Validate, RDML-RunView — [gear-genomics.com](https://www.gear-genomics.com/rdml-tools/) [65]. MIQE 2.0 names "RDES" as a raw-data format alongside RDML — [5].
- Allotrope Simple Model: schemas under `json-schemas/adm/<technique>/<maturity>/<year>/<month>/`; qPCR schema is `qpcr.embed.schema.json` at `json-schemas/adm/pcr/REC/2026/09/` (folder `pcr`, not `qpcr`); REC models are public, CR models "require membership access"; links "SHOULD NOT" be used in production — [ASM README](https://gitlab.com/allotrope-public/asm/-/raw/main/README.md) [54]. The repository's licence link is titled "Creative Commons Attribution Non Commercial 4.0 International" — [GitLab](https://gitlab.com/allotrope-public/asm) [54]. allotropy uses qPCR REC/2024/09 — [55].
- SiLA 2: sila_base and sila_python MIT — [50]. Benchling labels/printers services exist for barcode labels — [57]. CFX `.plrn` RunID "barcode identifying this run (30-character maximum, commas not allowed)"; API RunID "Typically populated with the plate barcode" — [12][13]. Benchling plates and containers carry "registry-unique" barcodes — [57].
- Sample-sheet naming conventions in the wild: QuantStudio Task values UNKNOWN/NTC/custom; CFX SampleType Unknown/Standard/Positive Control/Negative Control/NTC/NRT; LC480 "Target Unknown"/"Ref Unknown"/"Target Negative"; EPFL/Hamilton STND/NTC/UNKN — [7][12][16][15].

#### Inferences
- qPilot's RDML already has the slots for a plate map (`pcrFormat`, react id, sample type, `interRunCalibrator`, `quantity`), so "one plate-map object" can literally be an RDML file with an empty `<data>` section (plus a small sidecar for robot-only fields such as source tube and volume). This avoids inventing a format and keeps the record standard.
- ASM's CC BY-NC licence is a problem only if qPilot *redistributes* the schema files; emitting JSON that conforms to ASM (as allotropy does under MIT) is a format-compatibility question, not a code-licence one, but it should be flagged to counsel-minded users and avoided in the core.
- Standardising the four task vocabularies into one enum with per-vendor writers is a two-hour job that removes a whole class of import errors.

#### Gaps
- No reliable statistic on specimen misidentification/mix-up rates in research labs was fetched (clinical Q-Probes-type data exists but was not reached; do not quote numbers).
- Brady/2D rack-barcode practice pages were not fetched; 1D vs 2D barcode conventions are unverified here.
- Whether RDML's sample `type` enumeration in v1.3 is exactly {unkn, ntc, nac, std, ntp, nrt, pos, opt, ref} was not visible in the fetched portion of the source (only the default "unkn" and element names were seen).

### 1.7 Money and time (what could be sourced)
- Robot assembly of a full 384-well plate: ~30 minutes; reaction volumes 10 µL (384) / 15 µL (96); up to 64 assays × 192 samples per design [15].
- Opentrons claims users "could save hours of repetitive pipetting each week"; no figures, no error rates [37].
- Hamilton's method needs 3 technical replicates by default and a 20% safety margin on reagent volumes [15].
- No instrument, robot or LIMS price lists were reachable (Integra: quote only [48]). Clarida's pricing is in the brief; nothing found here changes it.

### 1.8 Where decisions are made and what "good" looks like
- Decisions made at design time: sample vs gene maximisation; which samples are IRCs; where NTC/NRT go (MIQE 2.0 expects both and expects the NTC frequency/Cq reported [5]); replicate counts per level (Kitchen 2010 says this should come from pilot variance, not habit [4]); edge-well policy [27].
- Decisions made at pipetting time: robot vs hand; safety margin; which combinations to drop ("User can force the Hamilton software to omit specific combinations" [15]).
- Decisions made at import time: how to name things so that the instrument accepts them and the analyst can match them [7][9].
- "Good" looks like EPFL's rule set: sample maximisation, 3 replicates, unique ASCII names, robot-generated instrument file, logbook entry [15]; plus Ruijter's "balanced and complete" overlap when plates must be split [2].

## 3. Discoveries (ranked by impact × feasibility × fit)

### D1. One plate-map object that compiles to the robot, the instrument and the analysis — with a round-trip check

1. **Persona and situation.** A PhD student or core-facility technician setting up a 2–8-plate SYBR or TaqMan study on a QuantStudio, CFX or LightCycler, with or without an Opentrons/Hamilton/Tecan, several times a month. Today they maintain the same layout in an Excel sheet, a robot file and the instrument editor.
2. **Evidence of the pain.** The EPFL chain (Excel `.xls` → Hamilton GUI in a Windows XP VM → `.txt` → QuantStudio) [15]; Thermo's "overwrite", "exact case", "unique names", "one sample per well" rules and checksum-protected plate files [7][9]; Bridges Lab's export→edit→import habit [11]; the Sharpie-on-printout SOP [33]; HTqPCR/pyQPCR/CopyCaller import failures [19][20][24]; P1, P2, P8, P9 above. Cost estimate: 20–60 minutes of re-typing per plate plus the occasional study lost to a transposed row (estimate; no published rate).
3. **What exists today.** Vendor editors (single instrument, no robot output); EPFL's one-way robot→instrument `.txt` [15]; Benchling's input generators (commercial, requires Benchling) [58]; wellmap (MIT) as a layout file format with no instrument or robot writers [31]; GPL R tools [28][30].
4. **The concrete feature.** `qpilot plate design|export|verify`:
   - **In:** a study design table (sample_id, group, batch factors, target_id, target_role reference/target, task {unknown, standard, ntc, nrt, pos, irc}, replicate n, quantity for standards, reporter/quencher per target, plate format 96/384) — CSV or the existing `qpilot plan` object.
   - **Object:** an RDML file with `pcrFormat`, one `react` per well (numeric id = `number + letter*columns` [65]), `sample/type`, `interRunCalibrator`, `quantity`, and no `<data>` yet, plus a sidecar `platemap.json` with robot-only fields (source labware, source well, volume, liquid class) and a content hash.
   - **Writers (deterministic, from the vendor specs cited):** QuantStudio TXT/CSV with `* Block Type` header lines and columns Well, Well Position, Sample Name, Task, Target Name, Reporter, Quencher [7][9]; CFX spreadsheet-importer tab-delimited template per fluorophore and CFX LIMS `.plrn` per Table 38 (PlateType, ScanMode, Units, RunID=plate barcode, RunProtocol, rows 17–113 wells, SampleType ∈ {Unknown, Standard, Positive Control, Negative Control, NTC, NRT}, CH1–CH5 targets, CollectionName, Replicate, quantities) [12]; LC480 9-column sample-information TXT (`General:Pos` ... `Rel Quant:Combined Sample/Target type`) [16]; Opentrons CSV for an `add_csv_file` runtime parameter plus a generated protocol skeleton [34][35]; Tecan GWL A/D/W records with numeric well indices [43][44]; a generic Hamilton CSV (comma separator, period decimals) [46]; and the core's Excel pair (sheets "DNA"/"PRIMER", tasks STND/NTC/UNKN) [15].
   - **Verify:** `qpilot plate verify --design platemap.rdml --instrument export.txt` parses the instrument's own plate-setup export (QuantStudio TXT, CFX CSV, LC480 TXT) or the run RDML and reports a well-by-well diff (missing wells, swapped names, wrong task/dye, extra wells) before or after the run. Mismatches become a Decision Card ("Instrument layout differs from design in 3 wells; options: trust design / trust instrument / exclude wells"), logged with a reason.
   - **Record:** design hash, every emitted file's hash, the diff result and the chosen resolution go into the Analysis Record; the plate barcode goes into CFX RunID / QuantStudio Experiment Name so it comes back in the data file.
   - **Agent:** MCP tools `qpcr_plate_design`, `qpcr_plate_export(target=...)`, `qpcr_plate_verify`.
5. **Feasibility.** All formats are documented in the sources above; RDML already has the fields; writers are plain text. Effort: QuantStudio + LC480 + Opentrons CSV + Tecan GWL writers and the verifier ≈ 1–2 weeks; CFX `.plrn` needs the vendor template CSVs from an installed CFX Maestro to lock row positions (≈ 3 days once a copy is available). Libraries: none needed beyond the standard library and the existing rdmlpython (MIT). Hardest part: keeping each vendor's naming constraints (case, uniqueness, forbidden characters, 256/30-character limits) in one validation layer, and the undocumented LC480 import variant.
6. **Why qPilot.** The Analysis Record is already RDML; the design becomes the first entry in the hash chain, so "as designed" vs "as run" is verifiable later; the robustness engine can treat layout conflicts as another axis; the MCP server lets an agent prepare a plate and a human approve it.
7. **Risks.** Vendor format drift (mitigate: golden-file tests per software version); users who never import (fine: the verifier still works on the exported run); CFX `.plrn` must be byte-exact. Confidence: high for QuantStudio/Opentrons/Tecan writers and the verifier; medium for CFX `.plrn` and LC480 import.

### D2. Design-time "can this study be analysed?" check (the plate-design assistant made concrete)

1. **Persona.** A scientist without a biostatistician planning 3+ plates; a core manager reviewing a client's design before booking the robot.
2. **Evidence.** Forum threads on combining plates after the fact [21][22]; qRAT's hard requirement for a common sample on every plate [6]; Hellemans' IRC rules and the 70%→40% error figure for 1 vs 3 IRCs [1]; Ruijter's "when more than 2 rounds of substitution are required, the design of the experiment is clearly incomplete" [2]; MIQE 2.0's per-run NTC/no-RT expectations [5]; Kitchen 2010's point that replicate numbers are "often uninformed" [4]; no permissive randomiser exists [28][30]; P4, P5, P12, P13.
3. **What exists.** qbase+ warns only at analysis time (paid); qRAT requires IPCs but does not design; PlateLayout randomises without qPCR controls (GPL-2); powerNest (2010) is not maintained; vendor editors have no notion of calibrators or overlap.
4. **Feature.** `qpilot plate design` takes the design table from D1 and produces per-plate layouts with:
   - **Allocation:** sample maximisation first (all samples of a target on one plate) [1][15]; when a target × sample set exceeds the plate, either (a) assign ≥3 IRC samples to every plate with the same IRC set [1], or (b) a balanced, complete overlap design for factor correction [2], user's choice.
   - **Controls:** NTC per target per plate and NRT per sample set per plate [5], positioned away from corners [27].
   - **Randomisation:** pseudo-block randomisation of samples within plates (reimplemented from the PlateLayout description: diagonal traversal, row/column block shuffles, Σ1/distance score, many iterations, lowest score wins) [28], keeping technical replicates non-adjacent [29], with batch factors (extraction date, RT batch) balanced across plates.
   - **Analysability facts (deterministic, computed before pipetting):** plate-overlap graph connectivity and number of substitution rounds needed (Ruijter Eq. 3 logic) [2]; IRC count and sameness across plates [1]; per-plate NTC/NRT presence [5]; the existing `qpilot plan` power / minimum detectable effect, now fed by pilot variance components if the user has a previous qPilot study (Kitchen 2010 pilot approach) [4]; edge-well exposure of controls and of the smallest groups.
   - **Decision:** a design-time Decision Card ranks the fixes ("add 2 IRCs to plates 2–4" / "move target X to plate 1" / "run one more plate") with the consequence for each gene; the user picks; the reason is logged.
   - **Record/agent:** the design, its facts and the decision enter the Analysis Record; MCP `qpcr_plate_design` returns the layouts and the fact list so an agent can propose but a human approves.
5. **Feasibility.** Pure combinatorics plus the published formulas; no datasets needed beyond the user's design; the robustness engine already exists. Effort ≈ 2 weeks including tests on synthetic designs. Hardest part: a good default when users refuse both IRCs and overlap (the tool should say plainly that plates will not be comparable, as qbase+ does by "assuming no inter-run difference" [1]).
6. **Why qPilot.** `qpilot plan` and the Decision Card machinery exist; impact ranking avoids nagging; the design becomes the first record entry (D1) and drives the later plate-correction choice (D3).
7. **Risks.** Over-constraining users with fixed layouts (keep "I'll use my own layout, just check it" as a mode); edge-well evidence for qPCR is thin, so present it as a soft rule [23][25]. Confidence: high for the analysability checks and sample-maximisation allocation; medium for randomisation benefits in qPCR (little qPCR-specific evidence).

### D3. Inter-plate correction as a robustness axis: Ruijter factor correction and Hellemans IRC side by side, on N0 from the raw curves

1. **Persona.** Anyone with ≥2 plates for the same target; the reviewer who asks "how did you combine plates?".
2. **Evidence.** Ruijter 2015's ~6-fold run difference example and its critique of calibrators [2]; the correction-on-Cq mistake [68]; qRAT scales Cq, not N0 [6]; forum confusion [21][22]; Factor-qPCR exists only as a closed Excel/RDML program [2][3]; P4–P6.
3. **What exists.** qbase+ (paid, IRC method); qRAT (IPC on Cq); Factor-qPCR (closed, 2015); the brief's roadmap headline "mixed model with plate effects" (statistical, not the published deterministic corrections).
4. **Feature.** A validated method module `plate_correction` with three options run through the robustness grid: none; IRC (geometric mean of IRC NRQs per gene per run; standard error propagated; refuse if the IRC set differs between runs) [1]; factor correction (N0 = Nq/E^Cq per well using qPilot's per-well efficiency, pairwise geometric-mean ratio matrix over shared conditions, nested substitution for missing pairs, plate factor = column geometric mean, divide, convert back to efficiency-corrected Cq with threshold 1 and the per-target reaction-weighted mean efficiency) [2]. Facts shown: plate factors with CIs, number of substitution rounds used, calibrator stability M [1], and whether conclusions change across the three options (this is the "agreement count" the robustness engine already reports). A Decision Card appears only when the options disagree on a conclusion. Agent: `qpcr_robustness` gains the axis automatically.
5. **Feasibility.** Equations are fully specified in the open-access paper [2]; qPilot already has E and Cq per well; no new dependency. Effort ≈ 1 week plus a public acceptance test on Ruijter's chicken-heart demo dataset (availability at hfrc.nl unverified) or a synthetic multiplicative-plate-effect dataset. Hardest part: defining "condition" overlap from the user's metadata (target × group × biological variable) robustly.
6. **Why qPilot.** Raw curves give per-well efficiency, which the factor method needs and Cq-only tools cannot provide; the design-time overlap check (D2) guarantees the correction is computable; everything lands in the record.
7. **Risks.** Users may expect a mixed model instead; present factor correction as the deterministic published route and keep the mixed model as a later axis. Confidence: high.

### D4. Opentrons / PyLabRobot closed loop: emit, push, run (with human start), and pull the as-pipetted log into the record

1. **Persona.** A lab-automation engineer or an automation-curious lab with an OT-2/Flex (or a Hamilton STAR/Vantage or Tecan EVO reachable through PyLabRobot), setting up qPCR plates weekly.
2. **Evidence.** Opentrons ships CSV-driven qRT-PCR prep protocols but the plate map still has to be written by hand and matched to the instrument [36]; the one-CSV, no-default, analysis-blocking constraints [34][35]; EPFL's robot generates the instrument file but through a 2000s GUI [15]; PyLabRobot exists to escape vendor software and is MIT [41][42]; robotools, the only Python GWL writer found, is AGPL [45]; P1, P3, P10.
3. **What exists.** Opentrons Protocol Designer/Library (no instrument file); PyLabRobot (no qPCR layer); vendor VENUS/FluentControl worklists; Benchling automation runs (commercial).
4. **Feature.** `qpilot robot opentrons` writes (a) a protocol `.py` (API ≥ 2.20) whose `add_parameters` declares one `add_csv_file` and whose `run()` reads source tube/well, destination well, volume for super-mastermix and template steps [34][35][37]; (b) the CSV from the D1 object. Optional `--push` uploads protocol and CSV to the robot over its HTTP API and creates the run, but never sends the "play" action: the technician starts it after deck check (safety: no automatic start) [39][40]. After the run, `qpilot robot pull` downloads the run record (commands, timestamps, errors) and stores its hash and a per-well "as-pipetted" table in the Analysis Record; wells with aborted or skipped commands become empty-well facts for the existing empty-well rules. For Hamilton/Tecan, `qpilot robot pylabrobot` emits a PyLabRobot script against a user-supplied JSON deck layout [41]; `qpilot robot tecan` writes a GWL directly (A/D/W records, numeric well indices) [43][44]. MCP: `qpcr_robot_export`, `qpcr_robot_pull`; the autonomy policy forbids `play`.
5. **Feasibility.** Opentrons docs are complete for the protocol side; the HTTP paths must be confirmed on a robot's `/redoc` [40]; PyLabRobot is MIT and supports STAR/Vantage/EVO/OT-2 [41]; Opentrons Flex coverage in PyLabRobot unverified. Effort: Opentrons path ≈ 1–2 weeks with a simulated robot (`opentrons_simulate`), Tecan GWL ≈ 2 days, PyLabRobot ≈ 2–3 weeks plus hardware access. Hardest part: labware definitions and liquid classes per site, and testing without hardware (PyLabRobot's visualiser and Opentrons simulation help).
6. **Why qPilot.** Closed-loop contract (actor = human/agent/system) already exists; the robot run becomes an actor whose output is hashed into the record; the same plate-map object feeds instrument and analysis (D1).
7. **Risks.** Hardware diversity; liability if a protocol is wrong (mitigate: dry-run mode, volume totals and tip counts shown on a Decision Card, no auto-start); small share of qPilot's academic users own robots today (cores and automation labs do). Confidence: medium-high for Opentrons, medium for PyLabRobot.

### D5. ELN/LIMS record push with exact objects: `.eln` RO-Crate for eLabFTW/RSpace, and Benchling plate-keyed results

1. **Persona.** Labs on eLabFTW (common in European academia; AGPL server) or Benchling (industry, some cores); core managers who must give clients a report and keep a chain of custody.
2. **Evidence.** eLabFTW's API has experiments, items, uploads, links, extra_fields, bookings and `.eln`/CSV import but no plate object [61]; Benchling has barcoded plates/wells, runs, result schemas (example qPCR schema with `ct`, `ct_mean`, `quantity`) and automation input/output processors [56][57][58]; Benchling's qPCR connectors go through Allotrope ASM (CC BY-NC schemas) [54][60]; cores keep a paper logbook and e-mail [15]; P11, P14.
3. **What exists.** Benchling's file-based QuantStudio/CFX connectors (Cq-level, commercial); allotropy (MIT) for ASM conversion [55]; generic "attach a PDF to the ELN".
4. **Feature.**
   - **`.eln` export:** write the Analysis Record (RDML + decision log + versions + checksums) as an RO-Crate zip per the ELN Consortium spec (MIT) so eLabFTW, RSpace, Kadi4Mat and SampleDB import it natively [62].
   - **eLabFTW push (API v2, MIT client):** `POST /experiments` (title = study, body = the templated methods paragraph), `POST /experiments/{id}/uploads` multipart `file` for the record zip and the RDML, `PATCH` with `metadatamerge` to write decision-log entries and Study Confidence as `extra_fields` (searchable via `/extra_fields_keys`), `POST /experiments/{id}/items_links/{item}` to the primer-pair and sample items, optional `POST /events/{instrument_item}` to log the instrument booking, and `canread`/`canwrite` set per lab policy [61].
   - **Benchling push:** `bulk_get(barcodes=[plate barcode])` to resolve the plate and wells, then `POST /api/v3/result` per well against a user-defined qPCR result schema (`sample_id`, `ct`, plus `n0`, `efficiency`, `study_confidence`), the record attached as a blob, or an `assay_run` with an output processor if the tenant uses Lab Automation [56][57][58].
   - **Core-facility report:** a client PDF/XLSX with the as-run layout (D1 verify), per-plate QC and the record hash; sample names can be replaced by the client's `custom_id` when the facility must not see or store client identifiers (policy flag, inferred need).
5. **Feasibility.** eLabFTW: a free docker instance for tests; Python client MIT; effort ≈ 1 week. `.eln`: spec on GitHub, effort ≈ 3 days (reuse the RO-Crate work already named as a stretch item). Benchling: needs a tenant and a schema; effort ≈ 1–2 weeks; SDK licence unverified (check before vendoring; use raw HTTP otherwise). Do not vendor ASM schema files (CC BY-NC) [54].
6. **Why qPilot.** The record is already hash-chained and versioned; an ELN entry pointing at it is the natural "sign-off" object; the MCP server can create the ELN entry as an agent action that waits in the approvals inbox.
7. **Risks.** ELN diversity; AGPL of eLabFTW is irrelevant for an HTTP client but must be explained; Benchling access for testing. Confidence: high for `.eln` + eLabFTW, medium for Benchling.

### D6. Three-way "as designed / as pipetted / as run" reconciliation with well-level provenance (chain of custody for research use)

1. **Persona.** Core managers and any lab that automates; also the reviewer-critic agent.
2. **Evidence.** EPFL's instruction to "Inspect the remaining volumes in the microtubes to detect putative inaccurate pipetting" and to fill a logbook [15]; CFX's RunID=barcode in `.plrn` and API [12][13]; MIQE 2.0's reproducibility/repeatability reporting items [5]; P1, P14.
3. **What exists.** Nothing joins the robot log, the instrument's plate setup and the analysis; Benchling's automation runs come closest (commercial).
4. **Feature.** Extend the record schema with a `provenance` block per well: designed (D1 object), pipetted (robot log row from D4 or "manual"), run (instrument export/RDML react), analysed (qPilot fact ids). A `records provenance` command prints the chain for any well and the diffs between stages; the reviewer-critic agent can cite "well B7: designed NTC, instrument says UNKNOWN, excluded by decision #12". Barcode fields are carried through where the vendor allows (CFX RunID, QuantStudio Experiment Name/Bar Code in reports [9]).
5. **Feasibility.** Mostly schema and glue once D1 and D4 exist; effort ≈ 1 week. Hardest part: instruments that never see the design (hand-typed layouts) — then the chain starts at the instrument export.
6. **Why qPilot.** Hash-chained record, actor model, MCP.
7. **Risks.** Perceived as regulatory overkill for research users unless shown only when something disagrees (fits the impact-ranked cards). Confidence: medium-high.

- Emit the core-facility Excel pair (EPFL "DNA"/"PRIMER") so clients of Hamilton-based cores can use D2 today [15].
